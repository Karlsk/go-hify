# Feature Specification: LLM 节点输出字段声明与变量下拉展开

**Feature Branch**: `014-workflow-llm-output-schema`

**Created**: 2026-09-23

**Status**: Draft

**Input**: User description: "模型输出 JSON 给 llm 节点加个输出约定声明并让下拉也能展开"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 声明输出字段并让下游下拉展开引用 (Priority: P1)

编排者希望 llm 节点「输出 JSON」时可被下游结构化引用：在检查器为 llm 节点声明输出字段（如 code、reason），此后所有下游节点（condition / llm / api / end）的变量下拉中出现该节点展开的字段条目（如 `{{llm1.code}}`），光标位置一键插入，无需手写、无需记忆字段名。

**Why this priority**: 用户原始诉求的核心动词——「加个输出约定声明并让下拉也能展开」；引擎 `{{node_key.field}}` 一级下钻（spec 08 FR9）已支持，缺的只是编辑期声明与提示，这是本篇 MVP。

**Independent Test**: 在编辑器为一条 llm 节点声明两个字段，保存后打开其下游节点的模板字段，下拉能分组列出该节点的字段条目并插入。

**Acceptance Scenarios**:

1. **Given** 一个含 llm 节点的工作流草稿，**When** 编排者在检查器为该 llm 节点声明输出字段（名称/类型/必填/说明）并保存，**Then** 图保存成功，声明随节点 config 持久化。
2. **Given** llm 节点已声明 code（string，必填）、reason（string，非必填），**When** 编排者打开其任意祖先下游节点的模板字段下拉，**Then** 该 llm 节点的分组出现 `{{llm1.code}}`、`{{llm1.reason}}` 字段条目（标注类型与必填），点击在光标处插入。
3. **Given** llm 节点未声明输出字段，**When** 打开下游变量下拉，**Then** 该节点仍只有整体引用条目 `{{llm1}}`，形态与现状一致（零回归）。

---

### User Story 2 - 运行期按声明校验模型回复 (Priority: P2)

运行期：声明了输出字段的 llm 节点，其回复在输出入池前按声明校验——回复须为合法 JSON 对象、必填字段齐、类型相符；不合规即该节点执行失败，错误信息含节点定位与具体字段，run 落 failed、节点轨迹可查。下游 `{{llm1.code}}` 下钻由此获得「声明即保证」的可信度，模型跑偏在 llm 节点当场暴露，而不是在下游 strict 渲染处报一个变量缺失。

**Why this priority**: 声明若只用于编辑期提示，下拉展开的条目对运行期是「善意谎言」；校验让声明成为契约，对齐 task 型 output_schema 的家族语义。

**Independent Test**: 构造声明了字段的 llm 节点，stub 模型分别返回：合规 JSON / 缺必填字段 / 非纯 JSON——断言前两者通过入池、后两者节点失败且错误含字段名。

**Acceptance Scenarios**:

1. **Given** llm 节点声明 code（必填），**When** 模型回复 `{"code":"A1","extra":1}`，**Then** 校验通过，回复原文入池，下游 `{{llm1.code}}` 下钻得到 `A1`（多余字段宽容）。
2. **Given** 同上，**When** 模型回复缺 code 字段或类型不符，**Then** 该节点执行失败，错误信息含节点定位与字段名，run 落 failed、节点轨迹记录失败态。
3. **Given** 同上，**When** 模型回复为纯文本或带 markdown 围栏的文本，**Then** 判非合法 JSON 对象，节点失败（不剥围栏、不纠偏重试）。

---

### User Story 3 - 存量工作流零影响 (Priority: P3)

所有未声明输出字段的既有 llm 节点（含嵌套子工作流内、chat 型工作流内）行为逐字节不变：消息序列不变、执行路径不变、记录形态不变、序列化往返不引入新键。声明是纯加法：只有显式声明了的节点才进入新路径。

**Why this priority**: 加法兼容是本篇能在不打扰任何存量图的前提下交付的前提（spec 011 同款先例）。

**Independent Test**: 既有全量测试零改动全绿；一张无声明的存量图序列化往返 diff 为空。

**Acceptance Scenarios**:

1. **Given** 任意存量工作流（llm 节点未声明输出字段），**When** 保存后读回并执行，**Then** 序列化往返零新键、执行行为与消息序列与声明特性引入前逐字节一致。
2. **Given** 嵌套子工作流内的 llm 节点声明了输出字段，**When** 父图执行到该子图，**Then** 子图内校验同样生效（子图独立游走，声明不跨图）。

---

### Edge Cases

- 模型回复 JSON 对象但被 markdown 代码围栏包裹（`` ```json ... ``` ``）：判非合法 JSON 对象、节点失败——不剥围栏（注入指令已要求纯 JSON 输出，围栏仍属不合规）。
- 声明字段全部为非必填、回复一个都没有：校验通过（宽容），下游若下钻该字段在 strict 渲染处报变量缺失（引擎既有语义，错误含变量名）。
- 字段声明与 input 或其他节点输出重名：不冲突——引用以 `节点key.字段` 二段式定位，基名不同即不同变量。
- 声明字段名含点号：与引擎一级下钻语义一致（字段名含点整体匹配不递归），声明允许但下拉插入的引用在运行期按整体字段名匹配——作者自担语义，不在本篇加限制。
- trial 试运行（spec 06/013）同样走声明校验——试运行即真实执行路径。
- 声明后修改字段（改名/删除）：下游既有 `{{llm1.旧字段}}` 引用不追改不标红（与 key 改名同策略，保存期 R10 兜底）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: llm 节点 config MUST 支持可选「输出字段」声明（键名与 task 型 `output_schema` 同名对齐的加法键）：未声明/空 = 现状零变化；字段集形态与 task 型 schema 字段一致（name / type / required / description）。（拍板 2026-09-23：完整字段形态，复用 task 型编辑器与校验）
- **FR-002**: 保存期对声明字段集做形态校验（name 非空不重名、type ∈ string/number/boolean），该校验仅对新键生效——存量无声明路径零新增拒绝。
- **FR-003**: 前端编辑器 llm 节点检查器 MUST 提供输出字段声明的行编辑表单（复用 task 型 schema 字段编辑形态）；readonly 态不渲染。
- **FR-004**: 前端变量下拉 MUST 对声明了输出字段的祖先 llm 节点按声明展开字段条目（`{{node_key.field}}` 可插入，条目标注类型与必填）；未声明的 llm 节点维持整体引用条目不变。
- **FR-005**: 运行期校验（严格）：llm 节点生成回复后、输出入池前按声明校验——未声明零校验；已声明：回复须为合法 JSON 对象、required 字段缺失拒、类型探针不符拒、多余字段宽容；失败 = 节点执行失败（错误含节点定位与缺失/不符字段名）。（拍板 2026-09-23：严格校验，对齐 task 型 output_schema 家族语义）
- **FR-006**: 声明非空时，系统 MUST 在渲染后的 user 消息末尾自动追加一段固定的 JSON 输出指令（语义：只输出一个 JSON 对象，逐一列出声明字段的名称、类型与必填性；指令为系统固定文案，本身不含用户变量、不做模板渲染，在 strict 渲染完成后追加）；追加后的完整 user 消息即实际发送与实际记录的内容（node_in 与 executions 反映实际发送文本，排障所见即所发）；未声明节点的消息序列与记录形态逐字节不变。（拍板 2026-09-23：自动注入；注入只发生在已声明节点，作者在 prompt 中的自行说明与注入文本共存不冲突）
- **FR-007**: 记录保真：未声明节点的 node_in / executions 形态逐字节不变；已声明节点按 FR-006 记录实际发送文本；声明本身不进运行记录新键（config 已含）；未声明的存量图序列化往返不引入新键。

### Key Entities *(include if feature involves data)*

- **输出字段声明（LLM 节点 config 内嵌字段集）**: llm 节点配置的可选组成部分；字段含 name（非空、节点内不重名）、type（string/number/boolean）、required（必填）、description（说明，可空）。不新增独立数据实体、不新增表、不新增迁移——随 workflow.config（jsonb）整体存取。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 为 llm 节点声明输出字段后，其所有下游节点的变量下拉 100% 出现对应字段条目且可一键插入（编辑期可发现性）。
- **SC-002**: 声明了必填字段的 llm 节点：运行期不合规回复 100% 被拦截，错误信息含节点与字段定位；合规回复 100% 通过且原文入池。
- **SC-003**: 未声明输出字段的存量工作流：保存/执行/序列化行为与本篇引入前逐字节一致（既有全量自动化测试零改动全绿）。
- **SC-004**: 既有变量下拉分组、既有表单与校验零回归（人工走查 manual-test 对应小节通过）。
- **SC-005**: 声明非空的 llm 节点，实际发给模型的消息 100% 含 JSON 输出指令且覆盖全部声明字段；未声明节点发给模型的消息逐字节不变。

## Assumptions

- 引擎 `{{node_key.field}}` 一级下钻语义（spec 08 FR9/O7②）不变，本篇只补「编辑期可知 + 运行期有保证」两环。
- 三项拍板（2026-09-23）：严格校验；自动注入 JSON 输出指令（系统在渲染后 user 消息末尾追加固定指令，记录实际发送文本）；完整字段形态（复用 task 型 schema 字段形态与编辑组件）。
- 模型不合规即失败，不做纠偏重试（注入提高合规率，但不承诺 100%）。
- 作者仍可在 prompt 中自行补充输出要求，注入文本与其共存（可能重复但不冲突）。
- 零迁移（config 为 jsonb 加法键）、零新增哨兵错误（复用 VALIDATION_FAILED 类）、零新增第三方依赖。
- 运行历史查询（runs 查询 API 与详情页轨迹查看）不在本篇——另立 spec 015 逐篇过各自的验收门。
- 前端遵循既有设计 token 冻结治理：新表单控件全用既有 token，不新增不修改 token 值。
